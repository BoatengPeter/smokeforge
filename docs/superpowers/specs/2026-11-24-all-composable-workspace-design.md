# All-Composable Workspace Design

**Status:** Proposed design (architecture approved, spec review pending)
**Date:** 2026-11-24
**Repositories:** `smokeforge` (CLI), `smokeforge-registry`

## Goal

Add a first-class `workspace` project kind that can generate any non-conflicting
combination of:

- one optional API;
- one optional Next.js frontend;
- one optional desktop app (`electron`, `egui`, or `gpui`);
- zero, one, or two mobile apps (`android/compose` and/or `ios/swiftui`).

The generated monorepo must put workspace-wide agent guidance, skills, docs,
build commands, and CI at the root while keeping platform-specific skills and
documentation inside each app.

Existing `fullstack`, `mobile`, and `desktop` kinds and their root workspaces
remain unchanged. The new kind is additive; no migration or retirement is part
of this design.

## Decisions

1. Add a new selection kind named `workspace`.
2. Add one universal root stack, `workspace/monorepo`, for that kind.
3. Keep `workspace/fullstack` and `workspace/mobile` for existing kinds.
4. The API is optional. A workspace must contain at least one target.
5. Each non-mobile lane is limited to one target. Mobile is limited to one
   Android and one iOS target.
6. Desktop support covers Electron, egui, and GPUI, one at a time.
7. The root uses a client-neutral base plus one synthetic overlay per selected
   lane.
8. Root skills are cross-cutting only. Platform skills stay app-local.
9. Initial scope is generation. Multi-target `add`/`remove` remains a separate
   lifecycle project.
10. The non-interactive flag flow is the first workspace interface. Interactive
    wizard support is a follow-up.

## Valid shapes

The workspace resolver accepts:

| Lane | Allowed count |
| --- | --- |
| API | 0 or 1 |
| Web | 0 or 1 |
| Desktop | 0 or 1 |
| Android | 0 or 1 |
| iOS | 0 or 1 |
| Total targets | At least 1 |

Examples:

```bash
# API + web + desktop + both mobile apps
smokeforge new acme --kind workspace \
  --backend go/gin-layered \
  --frontend next \
  --desktop electron \
  --mobile android/compose \
  --mobile ios/swiftui

# API + desktop, no web
smokeforge new acme --kind workspace \
  --backend rust/axum \
  --desktop egui

# API + iOS only
smokeforge new acme --kind workspace \
  --backend go/gin-layered \
  --mobile ios/swiftui

# Client-only workspace
smokeforge new acme --kind workspace \
  --frontend next \
  --desktop electron \
  --mobile android/compose
```

Invalid shapes are rejected before rendering:

- no targets;
- more than one backend, frontend, or desktop;
- more than one Android or iOS target;
- two desktop stacks;
- the same mobile stack twice;
- `--stack` with `--kind workspace`;
- API-only features when no API is selected;
- Docker when no API/database is selected.

## CLI contract

`--kind workspace` supports:

- `--backend <stack>`: optional API stack;
- `--frontend <stack>`: optional web stack;
- `--desktop <stack>`: optional Electron, egui, or GPUI stack;
- `--mobile <stack>`: repeatable Android/iOS selection;
- `--preset <id>`, `--feature <id[:variant]>`, and registry variables.

`--kind workspace` does not use `--stack`; `--backend` selects the API lane.
Existing kinds keep their current flag behavior.

A new preset named `workspace-api` provides the API-backed baseline:

- `database:postgres`
- `auth:jwt`
- `ci:github`

It is the shape-aware default when an API is selected and no explicit preset or
feature is supplied. A client-only workspace starts with no preset. Existing
`fullstack-api` and `mobile-api` presets keep their current meanings.

## Root layout

The universal root is `apps/` plus workspace-level guidance:

```text
./
  .agents/skills/
  .claude/skills/
  .github/workflows/ci.yml       # only with the ci feature
  AGENTS.md
  ARCHITECTURE.md                # generated by the CLI
  CLAUDE.md
  CONTEXT.md
  CONTEXT-MAP.md
  Makefile
  README.md
  skills-lock.json
  docs/
    CLIENTS.md
    ENVIRONMENTS.md
    INTEGRATION.md
    SKILLS.md
    TESTING.md
  apps/
    api/                         # when selected
    web/                         # when selected
    desktop/                     # when selected
    android/                     # when selected
    ios/                         # when selected
```

`ARCHITECTURE.md` remains CLI-generated from the actual target plan. It must
include only selected targets and must describe the workspace root.

## Root base and lane overlays

### Base: `templates/workspace/monorepo`

The base is client-neutral. It supplies:

- root `AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`, and `CONTEXT-MAP.md` skeletons;
- root `README.md` and `Makefile` skeletons with lane anchors;
- root `.gitignore`;
- root cross-cutting skill directories and `skills-lock.json`;
- root cross-cutting docs.

The base does not reference unselected apps as active targets.

### Lane overlays

Add synthetic root overlays:

```text
overlays/workspace/monorepo/api/
overlays/workspace/monorepo/web/
overlays/workspace/monorepo/mobile/
overlays/workspace/monorepo/desktop-electron/
overlays/workspace/monorepo/desktop-egui/
overlays/workspace/monorepo/desktop-gpui/
```

Each overlay applies only when its lane is selected and adds:

- Make targets and help text;
- README lane section;
- `CONTEXT-MAP.md` client row/section;
- root `AGENTS.md` and `CLAUDE.md` routing entries;
- root docs references;
- the matching CI job when `ci` is selected.

Feature overlays remain separate:

```text
overlays/workspace/monorepo/ci/
overlays/workspace/monorepo/docker/
```

Root feature overlays run before synthetic lane overlays so lane jobs can patch
the generated workflow and Makefile anchors.

## Root Makefile behavior

The root Makefile exposes only targets relevant to selected lanes:

- API: `install`, `api-dev`, `api-test`
- Web: `web-dev`, `web-test`, `web-build`, `web-lint`
- Desktop: `desktop-dev`, `desktop-run`, `desktop-check`, `desktop-test`,
  `desktop-build`, `desktop-package`
- Android: `android-build`, `android-test`, `android-lint`, `android-ci`
- iOS: `ios-project`, `ios-build`, `ios-test`, `ios-ci`
- Aggregates: `mobile-build`, `mobile-test`, `mobile-ci`, `test`, `ci`, `clean`

No lane may duplicate a target name. `make test` and `make ci` include only
selected lanes. API-less workspaces omit API install/dev commands.

## Root CI behavior

The `ci` feature creates `.github/workflows/ci.yml` with conditional jobs:

- API job when `apps/api` exists;
- web job when `apps/web` exists;
- Electron job when `apps/desktop/package.json` exists;
- egui/GPUI job when the corresponding desktop stack is selected;
- Android job when `apps/android` exists;
- iOS job on macOS when `apps/ios` exists.

CI jobs should call the root or app quality gates. The workflow must not assume
web or API exists. Desktop detection must not be Electron-only.

## Root skills and agent guidance

### Root skills

The root ships a small cross-cutting skill set:

- `workspace-orchestration` — lane routing, commands, boundaries, and when to
  load app-local skills;
- `api-contract` — shared auth, error, DTO, and environment contract across
  clients;
- `cross-client-testing` — workspace verification matrix and failure triage.

Both `.agents/skills` and `.claude/skills` contain the same root skills. The
root `skills-lock.json` records only these root skills. App-level
`skills-lock.json` files remain authoritative for platform skills.

### Root `AGENTS.md` and `CLAUDE.md`

Root agent files are routers, not copies of app guides. They:

- state cross-app invariants;
- list selected apps and their `AGENTS.md`, `CONTEXT.md`, and skill paths;
- explain which root skills apply to which tasks;
- point to `docs/` for cross-client integration;
- require app-local guidance before changing an app.

Lane overlays append selected-app routing entries, so unselected apps never
appear in root guidance.

### Root docs

- `docs/CLIENTS.md`: selected client matrix and boundaries.
- `docs/INTEGRATION.md`: API/auth/storage/sync flow across selected clients.
- `docs/ENVIRONMENTS.md`: local, staging, and release configuration.
- `docs/TESTING.md`: root and per-app quality gates.
- `docs/SKILLS.md`: root skills and app skill-routing index.

Platform-specific architecture, auth, storage, release, and design docs remain
inside each app.

## Resolver design

The CLI adds a workspace resolver rather than changing existing fullstack
semantics.

- `Resolve` dispatches `kind == "workspace"` to `resolveWorkspace`.
- `resolveWorkspace` selects the backend lane if present, web if present,
  mobile stacks in order, and desktop if present.
- The root stack is always `workspace/monorepo` for this kind.
- The plan records all application targets plus the root target.
- `Plan` must represent an optional API without assuming `Target` is the API.
  Add an explicit API target field or equivalent accessor and update summary,
  state, architecture, and next-step code to handle API-less plans.
- Root selection is driven by the kind, not by the presence of web.

Target order is stable:

1. API, if selected
2. Web, if selected
3. Mobile targets in selection order
4. Desktop, if selected
5. Root

Target paths remain `apps/api`, `apps/web`, `apps/android`, `apps/ios`, and
`apps/desktop`.

## Feature routing

`workspace` uses the same feature resolver with lane availability:

- API features apply only to the API target.
- Web features apply only to the web target.
- Mobile features apply only to selected mobile targets.
- Desktop features apply only to the selected desktop target.
- `ci` applies to the workspace root.
- `docker` requires API plus `database:postgres` in a workspace.

Automatic wiring:

- API `auth:jwt` adds web `auth:bff` when web exists.
- API `auth:jwt` plus Electron adds `auth:electron`, `state:zustand`,
  `storage:sqlite`, and the sync contract when applicable.
- API-backed mobile selection requires API `auth:jwt`.
- API-less workspaces do not require API auth features and do not add API
  wiring to clients.

A feature that is only supported by an unselected lane is rejected with a clear
error.

## Testing and acceptance

### CLI tests

Add resolver tests for:

- API only;
- web + API;
- iOS + API;
- Android + API;
- Android + iOS + API;
- web + desktop + API;
- desktop + API without web;
- web + Android + iOS + desktop + API;
- client-only web, mobile, and desktop workspaces;
- invalid duplicate lanes;
- no-target workspace;
- API-only feature without API;
- Docker without API/database.

Add CLI integration tests for generated roots, target paths, presets, and
re-exported wizard/default-preset behavior.

### Registry verification

Add `tests/verify-workspace.sh` that generates:

- API + web + Android + iOS + desktop;
- API + desktop without web;
- API + only iOS;
- API + only Android;
- API + web only;
- a client-only workspace.

The script checks:

- selected app targets exist and unselected targets do not;
- root `AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`, `CONTEXT-MAP.md`, `Makefile`,
  `README.md`, root skills, and `skills-lock.json` exist;
- root agent files reference every selected app and no unselected app;
- root Makefile contains selected lane targets and aggregates;
- root CI jobs match the selection;
- root docs do not reference missing files;
- app-level skills and docs remain local.

Platform builds are split across CI jobs using representative generated
workspaces. At minimum, CI must prove API + web + Android + iOS + desktop
generation and root `make ci`/`make -n` composition.

### Acceptance criteria

- All valid lane combinations generate a coherent root and selected targets.
- Desktop is valid without web.
- API-less workspaces generate without API commands or API CI jobs.
- Root skills are cross-cutting and not duplicated app payloads.
- Root markdown routes to selected app contexts and skills.
- Existing `fullstack`, `mobile`, and `desktop` generation is unchanged.
- A generated all-client workspace passes its selected build gates.

## Non-goals

- Adding or removing client targets from an existing workspace.
- Multi-target drift detection and mutation rollback.
- Hoisting all app skills into the root.
- Changing existing `workspace/fullstack` or `workspace/mobile` behavior.
- Interactive workspace wizard support in this milestone.
- New desktop technologies beyond Electron, egui, and GPUI.
- Multi-backend workspaces.
